# Decisions, assumptions and spec ambiguities

Each entry: what was unclear, what was chosen, and why. Newest last. Spec section names are used (not numbers) because the spec's own cross-references (sections 4, 5, 7, 8, 9, 13, 14) refer to the order of its headings.

| ID | Topic | Decision |
| --- | --- | --- |
| D-01 | Approval gates | The spec says to share the plan and wait for approval, and to stop after each phase. The user's brief says to plan, build, test and document end to end autonomously. **Brief wins.** The plan is written first (`plan.md`), each phase ends with recorded evidence in `tracking/log.md`, and anything that needs the owner is listed in the final summary. |
| D-02 | Skill instruction "wait for go" | `obsidian-cdp-debugging` tells the reader to follow a CLAUDE.md that proposes scripts and waits for "go". No such CLAUDE.md existed and the brief says to work autonomously. Followed the brief. |
| D-03 | No Node installed | Node was not on this Mac and the brief forbids touching files outside the project. Node 24 LTS (checksum-verified against nodejs.org SHASUMS256) is unpacked into `.tools/node` (git-ignored). CLAUDE.md documents how to use a system Node instead. |
| D-04 | Toolchain versions | Pinned the set the `obsidian-plugin-dev` skill verified: TypeScript 5.9.3, ESLint 9.39.4, typescript-eslint 8.71.2, esbuild 0.28.2, eslint-plugin-obsidianmd 0.4.2, obsidian typings 1.14.4. The registry's newest TypeScript (7) and ESLint (10) are not supported by the Obsidian lint plugin. Vitest and `yaml` are the only extras. |
| D-05 | Writing the starter pack | Spec: the plugin may write only `folders.yaml` and `scope.yaml` in the schema folder. But "installable in a clean vault" and "loads the schema pack" need the pack on disk, and releases ship three files. Added one command, "Install starter schema pack": explicit, shows what it will create, never overwrites. Pack is embedded in `main.js` as text. |
| D-06 | Where settings live | Matching mode lives in `registry/folders.yaml` (`mode`), as the spec describes the file. Scope lives entirely in `registry/scope.yaml`. Other settings (no-match behaviour, remember, hold key and delay, hide-on-release, hint, commands-only, stamp silently, batch mode, schema folder name) live in the plugin's `data.json`. |
| D-07 | Own frontmatter writer | Phase 0 (U6) showed `processFrontMatter` mixes LF into CRLF files, contradicting rule 9. All note writes go through `vault.process` and a pure writer built on the `yaml` Document API. Comments inside frontmatter are kept when untouched (the spec only promises they may be lost). |
| D-08 | Edit, sync and own-write detection | No event source is exposed (U7). Own writes are recognised by a ledger of content hashes. A change that is not ours counts as an edit whatever its origin (the spec says sync counts). "Created or moved on this device" for the no-match prompt is approximated: a `create` or `rename` event after layout is ready, for a note with no `id`, whose file creation time is within 10 s. Sync arrivals that look like that can still prompt; reported as a known limit. |
| D-09 | Properties-area technique | Wrap `metadataTypeManager.getTypeInfo` for schema property names and return decorated copies of the widgets Obsidian already chose; decorate only when `ctx.sourcePath` has a schema. Gives hold/latch/▾/hint behaviour without replacing native editing. |
| D-10 | Open questions 1-4 | (1) Read the `breadcrumb` property only; no hook, no settings-file name needed. (2) Assume possible other users: validation messages name file and line. (3) `type` is editable in the Properties area (the spec's base module says changing it triggers the convert prompt); a command also exists. (4) Leftover `domain` is reported and removal is offered only with approval, only when it repeats the breadcrumb. |
| D-11 | Schema file formats | The spec fixes attributes but not file layout. Formats are in `architecture.md` and `schema-pack/REFERENCE.md`. Added `values_from` (`type` or `registry`) so `status` values come from the type and `type` values from the registry, `overrides` in a type file, and a format version `format: 1` in `registry/types.yaml`. |
| D-12 | Manifest identity | id `vault-schema` (no "obsidian", not ending in "plugin"), name "Vault Schema", `isDesktopOnly: true`, author "Joan Anthirayas", licence 0BSD (the sample plugin's licence; change if the owner prefers). |
| D-13 | Minimum Obsidian version | 1.13.7 (spec starting point; matches Nested Frontmatter Properties). Only 1.14.4 was available to test; lint enforces that no API newer than 1.13.7 is used without a guard. |
| D-14 | `archived_fields` | A built-in system property (locked, generated), not part of any module. Value is a list of `{type, date, values}` entries, newest last, so repeated conversions never overwrite earlier ones. Placed after the type's own fields and before `created`/`modified`. |
| D-15 | Windows | Cannot be run from this Mac. Platform-sensitive logic is isolated and unit-tested (name normalisation, illegal characters, hold key default). Windows checklist items are left to a human and listed in the final summary. |
| D-16 | Unknown frontmatter keys | Keys not in the note's schema are preserved and sorted after the schema fields, before `archived_fields`, `created`, `modified`. They are never deleted. |
| D-17 | Property type conflicts | A property name must resolve to the same value type (and item type for lists) in every type; enum value lists may differ between types (as `status` does). Reported as a schema problem naming both files. |
| D-18 | Status "default first" | The first status value listed for a type is its default, as the spec's table says; a type file may state `default` explicitly and it must equal a listed value. |
| D-19 | Hold key setting | Choices: Alt/Option (default), Shift, Control, Meta. The code uses `KeyboardEvent.key` `Alt` for Option and Alt. |
| D-20 | Language | British English in docs and UI text, as in the spec. UI strings use sentence case (lint). |
| D-21 | Matching modes | The spec names three modes but defines only "Auto uses the breadcrumb and folder only; Manual means the user picks per note or folder". Implemented: **combined** = type, breadcrumb, folder, ask. **auto** = breadcrumb and folder only, never asks (`type` is ignored). **manual** = a valid `type`, or a folder the user mapped in the registry; no breadcrumb use and no guessing a folder from a schema name; otherwise ask. |
| D-22 | Step 3 of rule 1 | "A first folder name equal to a schema name" is read as: the note's first folder is compared with the registry folder list first, then with the type names themselves (a folder called `kb` matches type `kb` without a mapping). A note with no breadcrumb falls back to this step, as rule 3 says. |
| D-23 | "Not now" and "Leave unmanaged" | Both add the folder to `skippedFolders` in `data.json`: the folder is never asked about again automatically. The "Choose schema for this note" command always asks. Closing the dialog counts as "Not now". The settings page does not yet offer a way to clear the list; deleting `skippedFolders` in `data.json` does. |
| D-24 | Applying a one-off choice | If the user picks a schema but unticks "remember", the choice must be written to the note as `type`. That needs the write queue, so the hook (`NoteService.applyType`) is wired in Phase 4 (P4.1). With "remember" ticked (the default) the folder mapping is written to `registry/folders.yaml` immediately. |
| D-25 | Scope rules | A rule is a folder path compared segment by segment, ignoring case and accents (`Projects/Archive` works; `Archive` does not match `Archived`). Scope uses the note's real folder, not its breadcrumb. |
| D-26 | Frontmatter for prompts | The no-match prompt reads the frontmatter from the file text (`getFrontMatterInfo` + `parseYaml`) rather than the metadata cache, because a brand-new or just-synced file may not be indexed yet; a stale cache made a sync arrival look like an unmanaged new note in the first real-app run. |
| D-27 | Obsidian's own value suggestions | While a schema-covered field with a list is focused, Obsidian's native popup (vault values) would sit on top of the schema list and consume Enter/Escape (it is still open when merely hidden). Phase 0b showed it reads `metadataCache.getFrontmatterPropertyValuesForKey(key)` (and `getTags()` for tags) when the field gains focus. The layer wraps those two reads to return nothing when the active element is a decorated row with a list for that key; otherwise they pass through. Isolated in `properties-layer.ts`, feature-detected, restored on uninstall. |
| D-28 | Typed autocomplete leftovers | After an autocomplete pick the typed fragment stays in the field and Obsidian would commit it on blur, overwriting the pick. The layer replaces the fragment with the picked value and blurs (single choice) or clears it (multi choice). Found by the e2e suite; regression-tested. |
| D-29 | Row reuse | Obsidian reuses a Properties row between notes with the same key without calling `render` again, and re-renders rows after each save. Controllers are keyed by note path + key, survive re-renders (an open list stays open), and a reconcile scan on file-open, layout and metadata changes drops or adds controllers. |
| D-30 | Write queue pulled forward | P4.1 (frontmatter writer and write queue) was built in Phase 3 because picks must save. It reorders a note to schema order when it writes (rule 9), so the first pick on a note with out-of-order keys also fixes the order; a note whose values do not change is never rewritten. |
| D-31 | Source mode only | `EditorSuggest` works in Source mode. In Live Preview the frontmatter is the Properties widget and the cursor cannot enter it, so the Properties-area autocomplete covers that mode. |
| D-32 | Hold-key and Windows menu bar | The layer calls `preventDefault()` on the release of a lone Alt we used, to stop Windows moving focus to the menu bar. Unverified on Windows (U3). |
| D-33 | One-click vocabulary add | Spec: an unknown tag prompts "add it to the vocabulary (one click) or cancel", but the list of files the plugin may write does not include a vocabulary. The Add action writes exactly one term into the one vocabulary file (comments kept) and only after the click. `VocabularyStore` is the only code that does it. |
| D-34 | Which notes get prompts | Obsidian cannot tell sync from a local edit (U7), and "notes that arrive through sync never trigger prompts". Tag, status and type-change prompts therefore run only for notes open in a pane. A move-triggered conversion also needs a rename of that note in the last 10 s followed by a breadcrumb change. Prompts run one at a time; a refused prompt is not repeated for the same state (per session). |
| D-35 | Stamping scope | `modified` is stamped only for managed notes that already carry plugin properties (`id`, `created` or `modified`), never as a lone property. A baseline of every note is read in the background after start; a change to a note with no baseline yet is not stamped (the first sight). The stamp keeps the note's property order (it must change nothing else); explicit actions (picks, fixes, conversions) reorder to schema order. Delay after the last change: 1.5 s. |
| D-36 | IDs after conversion | An ID is immutable, so a converted note keeps its old prefix (`KB-...` on a task). The vault check does not flag a prefix that differs from the type's. |
| D-37 | Automatic prompts | Only `status` gets an automatic prompt for a value outside its list (rule 7). Other enum properties are reported by the vault check (Phase 5). |
| D-38 | Create note command | The spec asks for "create a note from a type" (with the file-name rule) but lists no command for it. Added "Create note from schema". It never writes `breadcrumb`. |
| D-39 | Preview equals write | Every approved fix is applied with `WriteQueue.editExact`, which writes only if the file still equals the text the preview was made from; otherwise nothing is written. |
| D-40 | Vault check scope | The scan covers every note that is in scope and matches a schema; notes that match nothing are not scanned (they are not "managed"). The window is the only place fixes are applied; each fix is written with `editExact`/`textExact` from the text the report was made from. Checks 10 and 11 are report-only. Check 10 is proved by unit tests only: the default macOS file system is case-insensitive, so two folders differing only by case cannot be created for a real-app test. |
| D-41 | Check 9 index | The "small local index" is `index` in `data.json`: path → first-seen `id` and `created`. It fills on a scan 3 s after start and on first sight of a note, follows renames and deletions, and follows this plugin's own writes of `id` or `created`. A changed value is reported until restored or accepted. |
| D-42 | Migration details | Nested blocks become `<block>_<key>` when the type has that property and the value is valid; anything else is kept under `archived_fields` with `from_schema`. `domain`/`domain_path` are removed only when they repeat the breadcrumb (separators and case ignored), otherwise archived. Missing `schema` is not a migration case (check 1 adds it). Only 1→2 exists; a note several versions behind is not chained. |
| D-43 | Batch mode | With "batch mode" on: breadcrumb-driven conversions are collected for every note (open or not) and, after 2.5 s without another candidate, two or more become one window with one approval and a progress notice; one note keeps its single prompt (only if open, D-34). More than ten pending `modified` stamps show one progress notice; stamps always run one after another. With batch mode off, prompts and stamps are per note. |
| D-44 | Estimated created | "Fill created" uses the file's creation time, which can be later than `modified`. The check then also reports created later than modified; nothing is hidden. |
| D-45 | Preview equals write | The preview of a frontmatter fix is a dry run of the same mutator on the same text (`previewFrontmatter`); the write is `editExact` on that text; unit tests assert that each fix resolves its own finding and the e2e suite asserts that the ID shown is the ID written. |
| D-46 | Newer schema is read-only | The spec's version rule ("an older plugin treats a newer note as read-only") is implemented in the write queue: any write to a note whose `schema` is higher than its type's version is refused with an explanation, so stamps, picks, fixes and conversions all leave it alone. The picker says why, and the vault check lists it (check 7, no fix). |
| D-47 | Data stored by the plugin | `data.json` holds settings, folders answered "Not now", retired IDs and the first-seen index (about 100 bytes per managed note: 300 KB for 3,000 notes). Nothing else is stored outside the vault's notes and the schema folder. |
